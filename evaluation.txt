Codexion
Codexion testing — Easy

Do not test with more than 200 coders.
Do not test with timing values under 60ms.
number_of_compiles_required must be at least 1: with 0, every coder has already "compiled at least 0 times" at startup and the simulation may stop immediately.
The first case below must burn out (it checks burnout detection); the other cases must run without any burnout and complete all required compiles.
Reference behaviour (use these as benchmark cases). Arguments are, in order:
number_of_coders time_to_burnout time_to_compile time_to_debug
time_to_refactor number_of_compiles_required dongle_cooldown scheduler

./codexion 1 800 200 200 200 10 0 fifo A single coder has a single dongle but needs two to compile. The coder can therefore never compile and MUST burn out, around timestamp 800.
./codexion 5 2000 200 200 200 10 0 fifo time_to_burnout (2000) is well above one compile+debug+refactor cycle (200+200+200 = 600), so no coder should burn out; the program must stop on its own once every coder has compiled at least 10 times.
./codexion 5 2000 200 200 200 7 0 edf Same, with the edf scheduler: no burnout, stops after 7 compiles each.
As there is no reference binary, these cases and their expected behaviour
ARE the benchmark. Because of OS scheduling, run each case several times and
expect the correct behaviour in the large majority of runs (allow a small
timing tolerance on borderline cases before counting them as failures).

Codexion testing — Less easy

Validate burnout edge cases.
Verify correct logging and timing tolerances.
Check no dongle duplication, correct state transitions.
Reference behaviour (benchmark cases):

./codexion 5 500 200 200 200 10 0 fifo Infeasible by design: one compile+debug+refactor cycle takes at least 200+200+200 = 600 ms, which is longer than time_to_burnout (500), so a coder cannot start its next compile in time and MUST burn out (around timestamp 500). The "burned out" line must be the LAST line printed and must appear within 10 ms of the deadline.
On a feasible run (for example the 5 2000 ... case from the Easy section), check that every "is compiling" line is immediately preceded by exactly two "has taken a dongle" lines for the same coder, and that no two log lines are ever interleaved on the same line.
Confirm the same dongle is never held by two coders at the same time (no dongle duplication).
Codexion testing — Medium

Verify cooldown behavior.
Test scheduler differences (edf vs fifo).
Validate refactoring timing and log serialization.
Reference behaviour (benchmark cases):

./codexion 5 3000 200 200 200 10 400 fifo Cooldown check: after a coder releases a dongle, that dongle must not be taken again until 400 ms have elapsed. By reading the timestamps, verify that no "has taken a dongle" line for a given dongle occurs within 400 ms of its release. time_to_burnout (3000) is generous, so no coder should burn out and the run should complete.
./codexion 5 3000 200 200 200 10 800 fifo then ... edf Run the exact same parameters once with fifo and once with edf. The large cooldown (800) forces coders to queue for the dongles. Compare the order in which the waiting coders are granted the dongles: under edf, a coder closer to its burnout deadline may be served ahead of one that requested earlier, so the grant order can differ from the strict arrival order seen with fifo.
Verify each coder spends close to time_to_compile / time_to_debug / time_to_refactor in each phase (within timing tolerance), and that the output stays correctly serialized even under heavy contention.
Codexion recode — FIFO to LIFO

Ask the evaluated student to turn the "fifo" scheduler into a "lifo" one: when several coders are waiting for the same dongle, it must now be granted to the coder whose request arrived LAST instead of first.
This change is observable at runtime, unlike a tie on EDF deadlines. Run the program once before the change and once after, with the SAME contention-heavy parameters (for example: ./codexion 5 3000 200 200 200 10 800 fifo), and compare the order in which the waiting coders acquire the dongles in the logs.
The recode is validated if the grant order under "lifo" is the reverse of the arrival order (the most recent requester is served first), while the rest of the program keeps working: no coder duplicates a dongle, logs stay serialized, and, with feasible parameters, no coder burns out.
Also read the code to confirm the change is made in the scheduler/queue logic itself and not faked at the log level.
